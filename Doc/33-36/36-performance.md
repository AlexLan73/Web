# Часть 1. Теория

## 36.1 Сначала измерь

Единственное правило, которое важнее всех остальных: **не оптимизируй по догадке**.

Интуиция о производительности в браузере ошибается систематически. То, что выглядит дорогим (много компонентов), часто бесплатно; то, что выглядит невинным (одна строка со стилем), роняет кадр.

**React DevTools Profiler:**
- запись → взаимодействие → стоп
- flame graph: ширина полосы = время рендера компонента
- ranked: самые дорогие сверху
- «Highlight updates» в настройках — подсветка перерисовок в реальном времени

Первое, что смотришь: **какие компоненты рендерятся, хотя не должны**.

**Performance-панель браузера** — для всего остального:
- длинные задачи (>50 мс) блокируют ввод
- Layout/Paint/Composite — что делает браузер после твоего JS
- Frames — красные означают пропущенные кадры

**`performance.mark`** для своих измерений:
```ts
performance.mark('fft-start');
const bins = computeFft(samples, config);
performance.mark('fft-end');
performance.measure('fft', 'fft-start', 'fft-end');
```
Появится в Performance-панели своей дорожкой.

**Бюджет кадра — 16.6 мс при 60 Гц.** Внутри: твой JS, стили, раскладка, отрисовка, композиция. На JS остаётся примерно 8-10 мс.

## 36.2 Порядок оптимизации

Из урока 20, теперь с полной картиной:

**1. Убрать лишнее состояние.** Производное считать при рендере, а не хранить.

**2. Опустить состояние вниз.** Состояние, нужное одному поддереву, живёт там.

**3. Композиция через children.** Элемент, созданный выше и переданный props, не пересоздаётся при рендере обёртки.

**4. Убрать данные из React.** Высокочастотные потоки — в ref, отрисовка через `rAF`. Уроки 34-35.

**5. Профилировать.**

**6. `memo` / `useMemo` / `useCallback`** — по результатам замера, вместе или никак.

**7. Виртуализация** — если проблема в количестве DOM-узлов.

**8. Воркер** — если проблема в вычислениях.

Пункты 1-4 бесплатны и улучшают структуру. Пункт 6 добавляет сложность. Начинать с шестого — типичная ошибка.

## 36.3 Три разных «медленно»

Диагноз определяет лечение.

**Много рендеров.** Компонент перерисовывается там, где не должен.
- Симптом: в Profiler десятки компонентов на одно взаимодействие
- Причина: состояние слишком высоко, нестабильные props, подписка на весь стор
- Лечение: пункты 1-3, селекторы Zustand (урок 29)

**Один рендер долгий.** Компонент рендерится редко, но по 100 мс.
- Симптом: одна широкая полоса в flame graph
- Причина: тяжёлое вычисление в теле, огромный список, сложное дерево
- Лечение: `useMemo`, виртуализация, разбиение компонента

**Тормозит браузер, а не React.** JS отработал за 2 мс, кадр занял 100 мс.
- Симптом: в Performance много Layout/Paint, мало Scripting
- Причина: тысячи DOM-узлов, дорогие CSS-свойства, layout thrashing
- Лечение: меньше узлов, другие свойства, `contain`

## 36.4 Виртуализация

Браузер плохо переносит больше нескольких тысяч DOM-узлов. Решение — рисовать только видимое.

```bash
npm i @tanstack/react-virtual
```

```tsx
const parentRef = useRef<HTMLDivElement>(null);

const virtualizer = useVirtualizer({
  count: runs.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 32,
  overscan: 8,
});

<div ref={parentRef} className="h-96 overflow-auto">
  <div style={{ height: virtualizer.getTotalSize(), position: 'relative' }}>
    {virtualizer.getVirtualItems().map(item => (
      <div
        key={runs[item.index]!.id}
        style={{
          position: 'absolute', top: 0, left: 0, width: '100%',
          height: item.size, transform: `translateY(${item.start}px)`,
        }}
      >
        <RunRow run={runs[item.index]!} />
      </div>
    ))}
  </div>
</div>
```

Пятьдесят тысяч строк — тридцать узлов в DOM. Прокрутка плавная.

**`transform: translateY` вместо `top`.** Трансформации обрабатываются композитором на GPU и не вызывают пересчёт раскладки. `top` вызывает.

**Цена виртуализации:** ломается поиск по странице (Ctrl+F), сложнее доступность, нужна известная или измеряемая высота строк. Для тысяч строк оправдано, для сотни — нет.

## 36.5 Что дорого в браузере

**Дорого при изменении:**
- `width`, `height`, `top`, `left`, `margin`, `padding` → пересчёт раскладки
- `box-shadow`, `filter`, `border-radius` на больших областях → отрисовка
- чтение `offsetWidth`, `getBoundingClientRect` сразу после записи стиля → принудительная синхронная раскладка

**Дёшево:**
- `transform`, `opacity` → только композиция, на GPU
- `will-change: transform` — предупреждение браузеру (но не злоупотребляй, каждый слой ест память)

**Layout thrashing** — чередование чтения и записи в цикле:
```ts
for (const el of elements) {
  el.style.height = el.offsetHeight + 10 + 'px';    // ❌ читаем после записи
}
```
Каждая итерация форсирует пересчёт раскладки. Разделяй фазы: сначала все чтения, потом все записи.

**`content-visibility: auto`** — браузер пропускает отрисовку невидимых блоков. Дешёвая альтернатива виртуализации для длинных страниц.

## 36.6 Вычисления

Тяжёлая математика в главном потоке недопустима — урок 01, теперь с инструментами:

**Воркер** для всего, что дольше нескольких миллисекунд. Пул по числу ядер, если задач много (урок 26).

**`SharedArrayBuffer`** — общая память без копирования вообще:
```ts
const shared = new SharedArrayBuffer(size * 4);
const view = new Float32Array(shared);
worker.postMessage({ buffer: shared });      // не transfer — оба видят одну память
```
Требует заголовков `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp`. Настраивается в `vite.config.ts` для dev и на сервере для прода.

С ней же работает `Atomics` — синхронизация и настоящая отмена расчёта:
```ts
const control = new Int32Array(new SharedArrayBuffer(4));
// главный поток: Atomics.store(control, 0, 1)
// воркер в цикле: if (Atomics.load(control, 0)) return;
```
Это закрывает недоделку из урока 26, где отмена только отклоняла промис.

**WebAssembly** — если алгоритм уже есть на C/C++. Через Emscripten компилируется и вызывается из воркера. Выигрыш над оптимизированным JS обычно 1.5-3x на численных задачах — не десятки раз, как иногда ожидают. JIT в V8 хорошо оптимизирует циклы по `Float32Array`.

Порядок: сначала вынести в воркер, потом оптимизировать алгоритм, и только потом WASM.

# Часть 2. Проработка

## Задача. Профилирование панели

Пройдём диагностику на реальном коде.

**Симптом 1: при движении ползунка перекрытия тормозит вся панель.**

Profiler показывает: рендерятся `AnalysisPage`, `Panel`, `SpectrumCanvas`, `RunList`, все 200 строк списка.

Диагноз: «много рендеров». Конфиг живёт в URL (урок 27), его изменение перерисовывает страницу целиком.

Лечение — пункты 2-3, без всякой мемоизации:
```tsx
// ❌ было: конфиг читается в родителе, всё под ним рендерится
export function AnalysisPage() {
  const [config, patch] = useConfigFromUrl();
  return (
    <>
      <ConfigEditor value={config} onChange={patch} />
      <SpectrumCanvas ... />
      <RunList runs={runs} />       {/* перерисовывается зря */}
    </>
  );
}

// ✅ стало: конфиг читается там, где нужен
export function AnalysisPage() {
  return (
    <>
      <ConfigPanel />               {/* useConfigFromUrl внутри */}
      <SpectrumPanel />             {/* свой доступ к конфигу */}
      <RunList runs={runs} />       {/* не знает про конфиг */}
    </>
  );
}
```

Каждый компонент подписывается на то, что ему нужно. Изменение перекрытия перерисовывает только `ConfigPanel` и `SpectrumPanel`.

**Симптом 2: при выделении строки в списке на 2000 элементов задержка 200 мс.**

Profiler: рендерятся все 2000 `RunRow`.

Диагноз: подписка на весь стор. Смотрим код:
```tsx
const { selectedIds, toggle } = useSelection();          // ❌ весь стор
const selected = selectedIds.has(run.id);
```

Лечение — селектор на срез (урок 29):
```tsx
const selected = useSelection(s => s.selectedIds.has(run.id));   // ✅ boolean
const toggle = useSelection(s => s.toggle);
```
Теперь перерисовываются две строки: та, что перестала быть выделенной, и та, что стала.

Замер после: 2 компонента вместо 2000, 3 мс вместо 200.

**Симптом 3: прокрутка списка дёргается, хотя рендеров нет.**

Profiler React пуст. Performance-панель: Scripting 3 мс, Layout 45 мс, Paint 30 мс.

Диагноз: «тормозит браузер». 2000 строк × 5 ячеек = 10000 DOM-узлов, каждая прокрутка — пересчёт раскладки.

Лечение — виртуализация (36.4). После: 30 строк в DOM, Layout 2 мс.

**Симптом 4: при запуске расчёта интерфейс замирает на 800 мс.**

Performance: одна длинная задача, внутри — `computeFft`.

Диагноз: вычисления в главном потоке.

Лечение — воркер (урок 26). После: главный поток свободен, интерфейс отзывчив, прогресс обновляется.

**Симптом 5: при потоке 60 Гц кадры пропускаются.**

Performance: 60 раз в секунду срабатывает React-рендер `AnalysisPage`.

Диагноз: данные текут через состояние.

Лечение — контур 3 (уроки 34-35): данные в ref, `getBins` вместо `bins`, отрисовка в `rAF`. После: ноль рендеров, стабильные 60 кадров.

**Итоговый замер конвейера:**
```ts
// src/lib/perf.ts
export function measure<T>(name: string, fn: () => T): T {
  const t0 = performance.now();
  const result = fn();
  const dt = performance.now() - t0;
  if (dt > 4) console.warn(`${name}: ${dt.toFixed(1)} мс`);
  return result;
}
```

Порог 4 мс — четверть кадрового бюджета. Всё, что дольше, стоит внимания.

Расставь по горячему пути: парсинг пакета, расчёт спектра, подготовка точек, отрисовка. Запусти на час — увидишь, что реально выбивается.

## Что получилось за курс

Панель, где:

- параметры в URL — воспроизводимо и можно поделиться
- настройки в Zustand с персистентностью
- ход расчёта — конечный автомат на `useReducer`, проверенный компилятором
- история на сервере через Query с кешем и оптимистичными обновлениями
- расчёт в воркере, главный поток свободен
- поток 60 Гц мимо React, отрисовка через `rAF`
- всё, что входит извне, валидируется схемами на границе
- домен — чистые функции, покрытые тестами без jsdom
- ни одного `any`, `strict: true`

Каждое из этих решений — прямое применение конкретного урока. Курс собирался так, чтобы в конце они сложились в работающую систему, а не остались набором приёмов.

# Часть 3. Домашка

**1.** Профилируй свою панель. Найди минимум три места из симптомов 1-5. Зафиксируй числа до и после — не «стало быстрее», а «200 мс → 3 мс».

**2.** Виртуализируй список прогонов. Сгенерируй 50 000 записей, замерь время прокрутки до и после. Проверь, что выделение и сортировка не сломались.

**3.** Пул воркеров по `navigator.hardwareConcurrency`. Замерь ускорение на пакете из 50 расчётов относительно одного воркера. Объясни, почему ускорение меньше числа ядер.

**4.** `SharedArrayBuffer` и `Atomics`. Настрой COOP/COEP-заголовки в Vite, реализуй настоящую отмену расчёта через флаг. Проверь, что воркер действительно останавливается, а не досчитывает.

**5.** Layout thrashing. Напиши компонент, который его вызывает, найди в Performance-панели «Forced reflow». Исправь разделением фаз чтения и записи.

**6.** Анализ бандла. Найди три самые тяжёлые зависимости. Для каждой реши: нужна, заменима или выносится в динамический импорт. Добейся начального чанка меньше 200 КБ.

**7.** Бюджет кадра. Расставь `performance.mark` по всему конвейеру: приём → парсинг → FFT → координаты → отрисовка. Построй разбивку по времени. Найди, где уходит больше всего, и оптимизируй именно это.

**8.** Итоговое. Возьми любой один компонент проекта и напиши разбор: какое состояние он держит и почему именно там, что перерисовывается при каждом виде взаимодействия, где границы с внешним миром и чем они защищены. Если на любой вопрос нет чёткого ответа — это место для рефакторинга.

# Что дальше

Курс закончен. Направления, куда двигаться:

**React 19 и Compiler.** Автоматическая мемоизация снимает большую часть урока 20. Actions и `useOptimistic` упрощают формы. Проверь, включён ли компилятор в твоём проекте.

**Серверные компоненты и Next.js.** Отдельный мир со своей моделью. Для приборной панели не нужен, для контентных приложений — стандарт.

**WebGL / WebGPU.** Когда canvas 2D упрётся: 3D-водопад, десятки каналов, сотни тысяч точек.

**WebAssembly.** Если есть готовый DSP-код на C++ — Emscripten позволяет использовать его напрямую.

**Playwright.** Тесты в реальном браузере: то, что jsdom не умеет (урок 32) — canvas, размеры, реальные события.

**Доступность.** Тема, которую я упоминала вскользь. Для внутреннего инструмента менее критично, но клавиатурная навигация окупается на любом проекте.
