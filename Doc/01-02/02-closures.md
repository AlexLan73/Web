# Часть 1. Теория

## 2.1 Определение

**Замыкание** — функция вместе с окружением, в котором она была создана. Внутренняя функция сохраняет доступ к переменным внешней даже после того, как внешняя завершилась.

```js
function outer() {
  const secret = 42;
  return () => secret;      // захватывает secret
}

const f = outer();          // outer завершилась
console.log(f());           // 42 — но secret жив
```

## 2.2 Отличие от C++

В C++ лямбда с захватом по ссылке `[&]` становится висячей, как только фрейм умер. Время жизни на тебе.

В JS фрейм **не умирает, пока на него кто-то ссылается**. Сборщик мусора держит окружение живым ровно столько, сколько живёт последняя ссылающаяся функция. Это `[&]`-захват, который никогда не протухает.

Практическое следствие в обе стороны:

- Не надо думать о времени жизни — компилятор и GC решают
- Легко случайно удержать в памяти большой объект: одна маленькая функция, захватившая переменную, не даёт освободить весь фрейм

## 2.3 Захватывается переменная, а не значение

Самый важный тезис урока.

```js
let x = 1;
const show = () => console.log(x);
x = 99;
show();        // 99, а не 1
```

Замыкание держит **ячейку**, не снимок. Читает при вызове, а не при создании.

## 2.4 Приватное состояние без классов

```js
function makeCounter() {
  let count = 0;                 // недоступна снаружи никак
  return {
    inc: () => ++count,
    dec: () => --count,
    get: () => count,
  };
}

const c = makeCounter();
c.inc();
c.inc();
console.log(c.get());            // 2
console.log(c.count);            // undefined — не достать
```

Три функции разделяют одну переменную `count`. Это настоящая инкапсуляция: нет ни `#private`, ни соглашения об именовании — переменная физически недоступна извне.

Каждый вызов `makeCounter()` создаёт **независимое** окружение. Два счётчика не мешают друг другу.

## 2.5 Классическая ловушка `var` в цикле

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3 3 3
```

`var` имеет функциональную область видимости — переменная **одна на весь цикл**. Все три коллбэка захватили одну и ту же ячейку. К моменту их вызова (следующий виток event loop — урок 01) цикл закончился, в ячейке `3`.

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0 1 2
```

`let` создаёт **новую привязку на каждой итерации**. Три разных ячейки, три разных замыкания.

До появления `let` это чинили через IIFE — немедленно вызываемую функцию, создающую свой фрейм:
```js
for (var i = 0; i < 3; i++) {
  (function(j) { setTimeout(() => console.log(j), 0); })(i);
}
```
Встретишь в старом коде. Сейчас просто пиши `let`.

**Правило: `var` не использовать никогда.** `const` по умолчанию, `let` там, где нужна перезапись.

## 2.6 Как устроен `useState`

Теперь ради чего всё это было. Мини-реализация хуков — 15 строк, объясняющих все странные правила React.

```js
const hooks = [];      // состояния всех хуков этого компонента
let cursor = 0;        // указатель текущего хука

function useState(initial) {
  const i = cursor;                          // ЗАХВАТЫВАЕМ ИНДЕКС в замыкание
  if (hooks[i] === undefined) hooks[i] = initial;

  const setState = (value) => {
    hooks[i] = value;                        // пишем по своему индексу
    render();
  };

  cursor++;
  return [hooks[i], setState];
}

function render() {
  cursor = 0;                                // сброс перед каждым рендером
  Component();
}

function Component() {
  const [count, setCount] = useState(0);
  const [name, setName] = useState('alex');

  console.log(`render: ${name} / ${count}`);

  if (count === 0) setTimeout(() => setCount(count + 1), 100);
}

render();
```

Вся магия — массив и целочисленный курсор. Никакой рефлексии, никакого анализа имён переменных.

`useState` **не знает**, что его вызвали для `count`. Он знает только, что это нулевой по счёту вызов в текущем рендере. Привязка состояния к переменной — исключительно по порядку вызова.

Замыкание здесь делает две вещи: `setState` захватывает свой `i` и остаётся привязанным к нужной ячейке навсегда.

## 2.7 Отсюда — правила хуков

**Почему нельзя вызывать хуки в условиях:**
```js
if (isLoggedIn) {
  const [user, setUser] = useState(null);   // ❌
}
const [theme, setTheme] = useState('dark');
```
При `isLoggedIn === true` `theme` — хук №1. При `false` — хук №0. Индексы разъезжаются, состояние одного хука подставляется в другой. Массив по индексу — вот и вся причина.

То же для циклов с переменным числом итераций и для раннего `return` перед хуком.

**Почему только на верхнем уровне компонента:** курсор глобальный и сбрасывается перед рендером конкретного компонента. Вызов из вложенной функции или коллбэка ломает привязку.

**Почему `setState` не мутирует, а заменяет:** React сравнивает старое и новое значение по ссылке (`Object.is`). Мутация на месте даёт ту же ссылку — React решит, что ничего не изменилось, и не перерендерит.

## 2.8 Stale closure

Самый частый баг в React, и корень его — ровно то, что мы разобрали в 2.3.

```js
function Component() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count);          // всегда 0!
    }, 1000);
    return () => clearInterval(id);
  }, []);                          // пустые deps — эффект создан один раз
}
```

Коллбэк интервала захватил `count` из **того рендера, в котором эффект создался**. Это был первый рендер, там `count === 0`. Новые рендеры создают новые замыкания с новыми значениями, но интервал держит старое.

Это не баг React — это прямое следствие того, что каждый рендер порождает свой набор функций со своим снимком переменных.

Лечится тремя способами, разберём подробно в блоке 2: функциональное обновление `setCount(c => c + 1)`, добавление зависимости в массив, или `useRef` как изменяемая ячейка.

## 2.9 Полезные паттерны на замыканиях

**Однократный вызов:**
```js
function once(fn) {
  let called = false, result;
  return (...args) => {
    if (!called) { called = true; result = fn(...args); }
    return result;
  };
}
```

**Мемоизация:**
```js
function memoize(fn) {
  const cache = new Map();
  return (...args) => {
    const key = JSON.stringify(args);
    if (!cache.has(key)) cache.set(key, fn(...args));
    return cache.get(key);
  };
}
```

**Debounce** — вызвать не раньше, чем через `ms` после последнего обращения:
```js
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}
```

Во всех трёх случаях состояние (`called`, `cache`, `timer`) живёт в замыкании — приватное, привязанное к конкретной обёртке.

# Часть 2. Проработка

## Задача. Мини-хуки с `useEffect`

Добавим к реализации из 2.6 эффект с зависимостями.

```js
const hooks = [];
let cursor = 0;

function useState(initial) {
  const i = cursor++;
  if (hooks[i] === undefined) hooks[i] = initial;
  return [hooks[i], v => { hooks[i] = v; render(); }];
}

function useEffect(fn, deps) {
  const i = cursor++;
  const prev = hooks[i];

  const changed = prev === undefined
    || deps === undefined
    || deps.some((d, k) => !Object.is(d, prev[k]));

  if (changed) {
    hooks[i] = deps;
    fn();
  }
}

function render() {
  cursor = 0;
  Component();
}
```

Что здесь важно:

- `useEffect` занимает **свою ячейку** в том же массиве — поэтому его тоже нельзя в условиях
- В ячейке хранится не состояние, а прошлый массив зависимостей
- `prev === undefined` — первый рендер, эффект выполняется всегда
- `deps === undefined` — зависимости не переданы, эффект на каждый рендер
- Сравнение поэлементное и **поверхностное** (`Object.is`). Новый объект или массив в deps каждый рендер = эффект каждый раз

Последний пункт — источник бесконечных циклов:
```js
useEffect(() => { ... }, [{ a: 1 }]);   // новый объект каждый рендер → всегда changed
```

Настоящий React дополнительно вызывает функцию очистки (возврат из `fn`) перед следующим запуском и при размонтировании. Механика та же — сохраняем возвращённое значение в той же ячейке.
