# Часть 1. Теория

## 1.1 Модель исполнения

JavaScript однопоточный. Один стек вызовов, одна куча, никаких мьютексов и атомиков.

Параллельности в языке нет вообще — есть **чередование**. Всё «долгое» (таймер, сеть, чтение файла) не выполняется в JS-потоке: оно передаётся рантайму (браузеру или Node), а обратно возвращается коллбэком в очередь.

Ближайшая аналогия из встраиваемых систем — суперцикл с обработчиками, которые **не могут вытеснить друг друга**. Прерывание не врывается в середину функции: оно ждёт, пока текущая функция полностью отработает.

Два следствия, оба важные:

**Хорошее.** Любая твоя функция выполняется атомарно. Гонок данных внутри функции не бывает никогда — не нужны блокировки, не нужны атомарные операции. Если между двумя строками кода нет `await`, никто туда не влезет.

**Плохое.** Блокирующий цикл замораживает вообще всё. В браузере вместе с логикой умирает и отрисовка: страница перестаёт реагировать на клики, анимации застывают.

## 1.2 Две очереди

Очередей задач две, и разница между ними — источник большинства сюрпризов.

| Микрозадачи | Макрозадачи |
|---|---|
| `Promise.then/catch/finally` | `setTimeout`, `setInterval` |
| продолжение после `await` | события DOM (клик, ввод) |
| `queueMicrotask()` | сетевые коллбэки, I/O |
| `MutationObserver` | `setImmediate` (Node) |

**Алгоритм цикла:**

1. Выполнить весь синхронный код до опустошения стека
2. Разгрести очередь микрозадач **полностью**, до дна
3. Взять **ровно одну** макрозадачу, выполнить
4. Вернуться к шагу 2

Ключевая асимметрия: микрозадачи выгребаются все, макрозадачи — по одной за виток.

Отсюда неочевидное: микрозадача, поставленная в очередь **во время** разгребания микрозадач, попадает в тот же проход. Бесконечная генерация микрозадач намертво вешает цикл — макрозадачи не получат управление никогда.

## 1.3 Базовый пример

```js
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve().then(() => console.log('C'));

queueMicrotask(() => console.log('D'));

console.log('E');
```

Вывод:
```
A E C D B
```

- `A`, `E` — синхронный код, всегда первый
- `C`, `D` — микрозадачи, как только стек опустел
- `B` — макрозадача, последняя, несмотря на нулевую задержку

**Ноль в `setTimeout` означает «в следующем витке цикла», а не «немедленно».** Более того, браузер клампит вложенные таймеры до минимум 4 мс после пятого уровня вложенности.

## 1.4 `async`/`await` — это разрезание функции

`await` не блокирует поток. Он **разрезает функцию на две части**: всё до `await` выполняется синхронно, всё после — становится микрозадачей.

```js
async function f() {
  console.log('1');     // синхронно, прямо сейчас
  await null;           // разрез
  console.log('2');     // микрозадача
}

f();
console.log('3');

// 1 3 2
```

`await null` — не «подождать null». Значение оборачивается в разрешённый промис, и остаток функции всё равно уходит в очередь. **Любой `await` создаёт разрез, даже с уже готовым значением.**

Мысленная модель: `async`-функция — это конечный автомат, где каждый `await` — точка сохранения состояния и выхода. Компилятор превращает линейный код в цепочку `.then()`.

## 1.5 Промисы энергичные

Критично, и на этом спотыкаются все, кто пришёл из Rust или C++ с ленивыми футурами.

**Работа стартует в момент создания промиса, а не в момент `await`.**

```js
const p = fetch('/data');   // запрос УЖЕ ушёл
doSomethingElse();          // он выполняется параллельно
const r = await p;          // просто забираем результат
```

Промис — не «описание работы», а **дескриптор уже запущенной работы**. `await` только подписывается на результат.

Отсюда разница в 500 мс между двумя вариантами:

```js
// Последовательно: 300 + 500 + 200 = 1000 мс
for (const { ms, name } of urls) {
  const v = await fake(ms, name);   // старт → ждём → старт следующего
}

// Параллельно: max(300, 500, 200) = 500 мс
const promises = urls.map(({ ms, name }) => fake(ms, name));  // все стартовали
const results = await Promise.all(promises);                  // ждём последний
```

`Promise.all` **ничего не запускает**. Он комбинатор ожидания над уже работающими промисами. Запуск произошёл в `map`.

## 1.6 Комбинаторы

| Метод | Поведение |
|---|---|
| `Promise.all` | все успешны → массив; любой упал → отказ первой ошибкой |
| `Promise.allSettled` | ждёт все, возвращает `{status, value/reason}` |
| `Promise.race` | первый завершившийся, успех или ошибка |
| `Promise.any` | первый **успешный**; все упали → `AggregateError` |

Важно: при отказе `Promise.all` остальные промисы **не отменяются**. Они продолжают выполняться, просто результат некому забрать. Отмены в промисах нет в принципе — для этого существует `AbortController`.

```js
const results = await Promise.allSettled(promises);
const ok = results.filter(r => r.status === 'fulfilled').map(r => r.value);
```

## 1.7 Блокировка потока

```js
function heavy() {
  const t = Date.now();
  while (Date.now() - t < 3000) {}
  return 42;
}

setTimeout(() => console.log('таймер'), 100);
console.log(heavy());
```

Таймер стоит на 100 мс, но сработает через три секунды. Никто не вытеснит занятый стек.

Хронология по шагам:

1. **0 мс** — `setTimeout` выполняется первым (он стоит строкой выше). Сам вызов мгновенный: он лишь регистрирует таймер («через 100 мс положи колбэк в очередь») и сразу возвращает управление.
2. **0 мс** — начинается `console.log(heavy())`: цикл `while` крутит главный поток 3 секунды, стек занят.
3. **~100 мс** — таймер истёк, среда кладёт колбэк `() => console.log('таймер')` в очередь макрозадач. Колбэк готов и ждёт — он не потерян и не отменён.
4. **~3000 мс** — `heavy()` вернул `42`, напечаталось `42`, стек опустел.
5. Только теперь event loop смог взять колбэк из очереди — печатается `'таймер'`.

Ключевая механика — в шагах 3–5: event loop достаёт задачи из очереди **только когда стек пуст**. Синхронный код никто не прерывает. Задержался не таймер (он сработал вовремя), а *обработка его колбэка*, потому что поток был занят. Поэтому «100 мс» в `setTimeout` означает «не раньше чем через 100 мс», а не «ровно через 100 мс».

Аналогия из C#: это как заблокировать UI-поток в WPF/WinForms тяжёлым циклом — `DispatcherTimer` тоже сработает только после того, как поток освободится и очередь сообщений снова начнёт обрабатываться.

Правило для тебя лично, когда дойдёшь до вычислений на клиенте: **тяжёлая математика в главном потоке недопустима**. Выносится в Web Worker — это настоящий отдельный поток ОС с обменом через сообщения. Между воркером и главным потоком нет общей памяти (кроме `SharedArrayBuffer`), поэтому и гонок нет.

## 1.8 Ловушки

**`map` не умеет ждать:**
```js
const bad = urls.map(async u => await fetch(u));
console.log(bad);   // [Promise, Promise, Promise] — не значения

const good = await Promise.all(urls.map(u => fetch(u)));
```

**`forEach` игнорирует async полностью:**
```js
arr.forEach(async x => { await save(x); });
console.log('готово');   // врёт, ничего не готово
```
Нужен `for...of` с `await` или `Promise.all(arr.map(...))`.

**Ошибка в async-функции без `await` — необработанный отказ:**
```js
async function risky() { throw new Error('oops'); }
risky();   // unhandled rejection, в Node падает процесс
```

# Часть 2. Проработка

Задачи, которые мы уже прошли, с эталонными решениями.

## Задача 1. Предсказать вывод

```js
async function f() {
  console.log('1');
  await null;
  console.log('2');
}
f();
console.log('3');
```

**Ответ:** `1 3 2`

Разбор: `f()` вызывается синхронно, печатает `1`. `await` разрезает функцию, остаток уходит в микрозадачи. Управление возвращается в основной код, печатается `3`. Стек пуст → разгребаются микрозадачи → `2`.

## Задача 2. Функция задержки

```js
const delay = ms => new Promise(resolve => setTimeout(resolve, ms));

await delay(500);
console.log('прошло полсекунды');
```

Что здесь происходит: создаём промис, внутри которого заводим таймер. Через `ms` таймер вызывает `resolve` — промис переходит в разрешённое состояние — продолжение после `await` встаёт в очередь микрозадач.

**Антипример — так не надо:**
```js
async function delay(ms) {
  const t = Date.now();
  while (Date.now() - t < ms) {}   // busy-wait
}
```
Функция технически «ждёт», но жрёт ядро на 100% и вешает весь event loop. Таймеры не тикают, промисы не резолвятся, UI мёртв.

## Задача 3. Последовательно vs параллельно

```js
const fake = (ms, name) =>
  new Promise(resolve => setTimeout(() => resolve(name), ms));

const urls = [
  { ms: 300, name: 'a' },
  { ms: 500, name: 'b' },
  { ms: 200, name: 'c' },
];

async function sequential() {
  const t0 = Date.now();
  const result = [];
  for (const { ms, name } of urls) {
    result.push(await fake(ms, name));
  }
  console.log(`sequential: [${result}] за ${Date.now() - t0} мс`);
}

async function parallel() {
  const t0 = Date.now();
  const promises = urls.map(({ ms, name }) => fake(ms, name));
  const result = await Promise.all(promises);
  console.log(`parallel: [${result}] за ${Date.now() - t0} мс`);
}

await sequential();   // ~1000 мс
await parallel();     // ~500 мс
```

**Объяснение разницы при одном потоке:**

Ожидание не занимает поток. Все три `setTimeout` тикают в рантайме одновременно — это не JS-код, это службы браузера/Node. Поток свободен всё это время.

В последовательном варианте мы искусственно сериализуем: второй таймер не заводится, пока не сработал первый. В параллельном все три заводятся сразу в `map`, дальше ждём самый долгий.

**Важно:** порядок результатов в `Promise.all` соответствует порядку входного массива, а не порядку завершения. `c` резолвится первым (200 мс), но в массиве останется третьим.
