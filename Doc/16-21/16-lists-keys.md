# Урок 16. Списки и `key`

`key` мы затронули в уроке 15. Здесь — подробно, потому что это единственное место в React, где неправильный код выглядит рабочим и ломается только на определённых действиях пользователя.

---

# Часть 1. Теория

## 16.1 Рендер коллекции

```tsx
{items.map(item => <Row key={item.id} item={item} />)}
```

`map` возвращает массив элементов. React умеет рендерить массивы напрямую — обёртка не нужна.

Работают все методы из урока 04, и их можно комбинировать в конвейер:
```tsx
{items
  .filter(i => i.visible)
  .sort((a, b) => b.value - a.value)
  .slice(0, 20)
  .map(i => <Row key={i.id} item={i} />)}
```

**Осторожно с мутирующими методами.** `sort` меняет массив на месте — если `items` пришли из props или состояния, ты их испортишь:
```tsx
{[...items].sort(byValue).map(...)}       // ✅ копия
{items.toSorted(byValue).map(...)}        // ✅ современный вариант
```

Тяжёлые конвейеры выполняются на каждом рендере. Пока список меньше нескольких сотен элементов — не думай об этом. Больше — `useMemo` (урок 20). Тысячи строк — виртуализация (`@tanstack/react-virtual`), иначе браузер задохнётся на самом DOM, а не на React.

**Фрагмент с ключом** — когда на элемент данных приходится несколько узлов:
```tsx
{items.map(item => (
  <Fragment key={item.id}>
    <dt>{item.label}</dt>
    <dd>{item.value}</dd>
  </Fragment>
))}
```
Короткая форма `<>` ключ не принимает — нужен полный `<Fragment>`.

## 16.2 Что делает `key` на самом деле

При сравнении двух версий списка React сопоставляет детей **по ключу**, а не по позиции.

Без ключей сопоставление идёт по индексу: первый со первым, второй со вторым. Вставка элемента в начало приводит к тому, что каждый узел сравнивается с данными соседа — React считает, что у всех изменились props, и обновляет все.

С ключами React строит соответствие «ключ → элемент» и понимает: это тот же узел, просто переехал. Вместо перерисовки всего списка — одна вставка.

**Ключ — не идентификатор данных, а идентификатор экземпляра компонента.** Разница проявляется в двух вещах:

1. **Состояние компонента** привязано к ключу. Сменился ключ — состояние сброшено, компонент смонтирован заново
2. **DOM-узел** переиспользуется при том же ключе, включая фокус, позицию прокрутки, состояние `<input>`

## 16.3 Почему индекс — плохой ключ

```tsx
{items.map((item, i) => <Row key={i} item={item} />)}
```

Проблема не в производительности, а в **привязке состояния к позиции вместо данных**.

Сценарий. Список из трёх строк, у каждой развернуты детали или введён текст в поле:

```
key=0  →  Сигнал A  [развёрнут]
key=1  →  Сигнал B
key=2  →  Сигнал C
```

Удаляем первую строку. Теперь:
```
key=0  →  Сигнал B  ← сюда переехало состояние "развёрнут" от A!
key=1  →  Сигнал C
```

React увидел: `key=0` был и остался, значит это тот же компонент, надо обновить props. Внутреннее состояние осталось от предыдущего жильца. Данные сдвинулись, состояние — нет.

То же при сортировке, фильтрации, вставке в середину, drag-and-drop.

**Когда индекс допустим:** список полностью статичен — не меняется порядок, ничего не добавляется и не удаляется, у элементов нет внутреннего состояния и нет неконтролируемых полей ввода. Например, отрисовка фиксированной таблицы констант.

Даже тогда лучше взять что-то из данных. Индекс — сигнал «здесь может быть баг».

## 16.4 Где взять ключ

**По убыванию предпочтительности:**

1. **id из данных** — идеально
2. **Естественный уникальный ключ** — имя файла, частота, код. Работает, если гарантированно уникален среди соседей
3. **Составной ключ** — `` key={`${row}-${col}`} `` для таблиц
4. **id, сгенерированный при создании** — если данные создаются на клиенте:
```tsx
const addItem = () => setItems(xs => [...xs, { id: crypto.randomUUID(), value: 0 }]);
```

**Чего не делать:**
```tsx
key={Math.random()}          // новый ключ каждый рендер → полное пересоздание
key={JSON.stringify(item)}   // меняется при любом изменении → сброс состояния
key={index}                  // см. выше
```
`Math.random()` — худший вариант: список размонтируется и монтируется заново на каждом рендере. Потеря фокуса, сброс анимаций, тормоза.

## 16.5 Требования к ключу

- **Уникален среди соседей**, не глобально. Два разных списка могут использовать одинаковые ключи
- **Стабилен между рендерами** для одного логического элемента
- Строка или число
- Не читается из компонента — `props.key` не существует. Если id нужен внутри, передавай отдельно:
```tsx
<Row key={item.id} id={item.id} />
```

## 16.6 `key` вне списков — сброс состояния

Второе применение, не связанное со списками. Смена ключа заставляет React считать компонент новым:

```tsx
<Editor key={selectedId} config={configs[selectedId]} />
```

При переключении записи `Editor` монтируется заново — все черновики, фокус, ошибки валидации сбрасываются. Это самый чистый способ решить проблему «состояние не обновляется при смене props» из урока 15.

Альтернатива — синхронизировать вручную через эффект — хуже: лишний рендер со старыми данными, больше кода, легче ошибиться.

## 16.7 Типизация

```tsx
type Props<T> = {
  items: readonly T[];
  getKey: (item: T) => string | number;
  renderItem: (item: T) => React.ReactNode;
};

function List<T>({ items, getKey, renderItem }: Props<T>) {
  return <ul>{items.map(i => <li key={getKey(i)}>{renderItem(i)}</li>)}</ul>;
}
```

Дженерик-компонент — подробно в уроке 23. `readonly T[]` в props правильнее обычного массива: компонент не должен его менять, и так туда можно передать результат `as const`.

`React.ReactNode` — тип всего, что React умеет рендерить: элементы, строки, числа, массивы, `null`, `false`.

# Часть 2. Проработка

## Задача. Список анализов с состоянием в строках

Добавляем в `dsp-panel` список сохранённых прогонов. У каждой строки — раскрываемые детали, то есть собственное состояние. Это делает проблему ключей наглядной.

```tsx
// src/types.ts — добавить
export type Run = {
  id: string;
  label: string;
  config: FftConfig;
  peakHz: number;
  elapsedMs: number;
};
```

```tsx
// src/RunRow.tsx
import { useState } from 'react';
import { WINDOWS, type Run } from './types';

type Props = {
  run: Run;
  onDelete: (id: string) => void;
};

export function RunRow({ run, onDelete }: Props) {
  const [expanded, setExpanded] = useState(false);

  return (
    <li className="run-row">
      <button onClick={() => setExpanded(e => !e)}>
        {expanded ? '▾' : '▸'} {run.label}
      </button>
      <span>{run.peakHz.toFixed(1)} Гц</span>
      <button onClick={() => onDelete(run.id)}>Удалить</button>

      {expanded && (
        <dl>
          <dt>Размер</dt><dd>{run.config.size}</dd>
          <dt>Окно</dt><dd>{WINDOWS[run.config.window].label}</dd>
          <dt>Время</dt><dd>{run.elapsedMs} мс</dd>
        </dl>
      )}
    </li>
  );
}
```

```tsx
// src/RunList.tsx
import { useState } from 'react';
import { RunRow } from './RunRow';
import type { Run } from './types';

type SortBy = 'label' | 'peakHz' | 'elapsedMs';

export function RunList({ runs, onDelete }: {
  runs: readonly Run[];
  onDelete: (id: string) => void;
}) {
  const [sortBy, setSortBy] = useState<SortBy>('label');

  const sorted = [...runs].sort((a, b) =>
    sortBy === 'label'
      ? a.label.localeCompare(b.label)
      : b[sortBy] - a[sortBy]
  );

  if (runs.length === 0) return <p>Нет сохранённых прогонов</p>;

  return (
    <>
      <select value={sortBy} onChange={e => setSortBy(e.target.value as SortBy)}>
        <option value="label">По названию</option>
        <option value="peakHz">По частоте пика</option>
        <option value="elapsedMs">По времени</option>
      </select>

      <ul>
        {sorted.map(run => (
          <RunRow key={run.id} run={run} onDelete={onDelete} />
        ))}
      </ul>
    </>
  );
}
```

**Разбор.**

**`[...runs].sort(...)`** — копия обязательна. `runs` пришли из props, мутировать их нельзя. Забудешь копию — в лучшем случае странное поведение, в худшем React вообще не заметит изменения, потому что ссылка та же.

**Ранний возврат для пустого списка** после хука. Порядок важен: `useState` вызван до `if`, иначе нарушено правило хуков (урок 21).

**`onDelete` приходит сверху** — строка не владеет данными, только сообщает о намерении. Однонаправленный поток, урок 17.

**Теперь эксперимент, ради которого всё это.**

1. Разверни детали у второй строки
2. Переключи сортировку

С `key={run.id}` — раскрытая строка остаётся раскрытой, просто переехала на новую позицию. Правильно.

Теперь замени на `key={index}`:
```tsx
{sorted.map((run, i) => <RunRow key={i} run={run} onDelete={onDelete} />)}
```

Повтори те же действия. Раскрытым останется элемент **на той же позиции**, а не тот, который ты раскрывал. Состояние привязалось к номеру строки вместо данных.

Проверь и удаление: разверни последнюю строку, удали первую. С индексами состояние съедет.

**Второй эксперимент — `key` как сброс.** В `App` добавь редактор конфига выбранного прогона:
```tsx
{selected && <ConfigEditor key={selected.id} initial={selected.config} />}
```
Внутри `ConfigEditor` пусть будет `useState(initial)`. Без `key` при переключении прогона поля останутся от предыдущего — состояние проинициализировалось один раз при монтировании. С `key` компонент пересоздаётся, и поля соответствуют выбранной записи.
