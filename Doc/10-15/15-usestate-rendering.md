# Урок 15. `useState`, рендер, реконсиляция

Устройство `useState` мы уже разобрали в уроке 02 — массив и курсор. Здесь про то, как это встроено в цикл рендера и что реально происходит между вызовом `setState` и изменением пикселей на экране.

---

# Часть 1. Теория

## 15.1 Состояние — это снимок

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

Ключевая мысль: **`count` — константа внутри одного рендера**. Не переменная, которая меняется, а значение, зафиксированное для этого конкретного вызова функции.

Каждый рендер — отдельный вызов `Counter()` со своим `count`, своими обработчиками, своим замыканием. Рендер №1 знает `count === 0` и ничего не знает о будущем.

Отсюда классический сюрприз:
```tsx
<button onClick={() => {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}}>
```
Прирост будет **1, а не 3**. Все три вызова видят один и тот же `count` из текущего рендера — скажем, 0 — и трижды планируют «поставить 1».

**Функциональное обновление** решает:
```tsx
setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);
// +3 — каждая функция получает результат предыдущей
```

Правило: если новое значение зависит от старого — всегда функциональная форма. Это же лечит stale closure из урока 02.

## 15.2 Пакетирование обновлений

`setState` **не** перерисовывает немедленно. Он ставит обновление в очередь.

```tsx
function handle() {
  setCount(1);
  console.log(count);      // старое значение! рендера ещё не было
  setName('x');
  // один рендер на оба обновления
}
```

React группирует все обновления в пределах одного события и делает **один** рендер. С React 18 это работает везде: в промисах, таймерах, нативных обработчиках — раньше только в синтетических событиях.

Это не оптимизация «на всякий случай», а гарантия консистентности: UI никогда не покажет промежуточное состояние, где `count` уже новый, а `name` ещё старый.

## 15.3 Что вызывает ререндер

Только два повода:
1. Изменилось состояние компонента
2. Перерендерился родитель

**Изменение определяется через `Object.is`** — сравнение по ссылке для объектов:
```tsx
const [cfg, setCfg] = useState({ size: 1024 });

cfg.size = 2048;
setCfg(cfg);              // ❌ та же ссылка — React ничего не сделает

setCfg({ ...cfg, size: 2048 });   // ✅ новая ссылка
```

Это причина, по которой всё состояние иммутабельно (урок 04). Не идеология, а механика сравнения.

Обратная сторона: `setCfg` с **тем же** значением React пропускает — рендера не будет. Но иногда он всё же отрисует компонент один раз, прежде чем понять, что менять нечего; на детях это не отразится.

## 15.4 Реконсиляция

После рендера React имеет два дерева описаний — старое и новое. Задача: найти минимальный набор изменений DOM.

Полное сравнение деревьев — O(n³). React использует эвристику за O(n), опираясь на два допущения:

**1. Разный тип элемента → поддерево пересоздаётся целиком.**
```jsx
{isEditing ? <Input value={v} /> : <Text value={v} />}
```
При переключении старый узел уничтожается со всем состоянием, новый монтируется с нуля.

**2. Позиция в дереве определяет тождество.**

Компонент в той же позиции того же типа считается тем же самым — его состояние сохраняется, props обновляются.

Отсюда неочевидное поведение:
```jsx
{isA ? <Counter /> : <Counter />}
```
При переключении счётчик **сохранит** состояние — для React это один и тот же элемент в одной позиции. А так:
```jsx
{isA ? <div><Counter /></div> : <span><Counter /></span>}
```
состояние сбросится — изменился тип родителя.

**Управление тождеством через `key`:**
```jsx
<Counter key={userId} />
```
Смена `key` — явный сигнал «это другой экземпляр». Состояние сбрасывается. Приём для форм: `<Form key={editingId} />` очищает поля при переключении редактируемой записи.

## 15.5 Списки и `key`

При сравнении массива детей React сопоставляет элементы по `key`, а не по позиции.

```jsx
{items.map(item => <Row key={item.id} {...item} />)}
```

**Без `key`** — сопоставление по индексу. Вставка в начало списка приводит к тому, что React считает, будто у всех элементов изменились props, и перерисовывает всё, попутно перепутав их внутреннее состояние.

**Индекс как `key`** — та же проблема:
```jsx
{items.map((item, i) => <Row key={i} {...item} />)}
```
Работает, только если список статичен: не сортируется, не фильтруется, элементы не вставляются и не удаляются в середине. Как только порядок меняется, `key={0}` начинает указывать на другой объект, и состояние строк (раскрытые детали, введённый текст, фокус) перемешивается.

Правильный `key` — стабильный идентификатор из самих данных. Если его нет, генерируй при создании элемента, а не при рендере.

**`key` должен быть уникален среди соседей**, не глобально.

## 15.6 Структурирование состояния

**Правило 1. Не хранить производное.**
```tsx
// ❌
const [items, setItems] = useState([]);
const [count, setCount] = useState(0);       // рассинхронизируется

// ✅
const count = items.length;                   // считается при рендере
```
Каждое дублирующее поле состояния — потенциальный рассинхрон. Всё, что вычислимо, вычисляй в рендере. Дорого — `useMemo` (урок 20), но сначала убедись, что действительно дорого.

**Правило 2. Группировать то, что меняется вместе.**
```tsx
// ❌ два состояния, всегда обновляются парой
const [x, setX] = useState(0);
const [y, setY] = useState(0);

// ✅
const [pos, setPos] = useState({ x: 0, y: 0 });
```

**Правило 3. Избегать противоречивых состояний.** То самое размеченное объединение:
```tsx
// ❌
const [loading, setLoading] = useState(false);
const [data, setData] = useState(null);
const [error, setError] = useState(null);

// ✅
const [state, setState] = useState<Analysis>({ status: 'idle' });
```

**Правило 4. Не дублировать props в состояние.**
```tsx
// ❌ при изменении props состояние не обновится
function View({ config }) {
  const [local, setLocal] = useState(config);
}
```
Это заморозит начальное значение навсегда. Если нужна редактируемая копия — сбрасывай через `key` на родителе.

**Правило 5. Уплощать вложенность.** Обновление на четвёртом уровне вложенности — три уровня spread. Либо нормализуй (словарь по id), либо бери Immer.

## 15.7 Типизация `useState`

```tsx
const [count, setCount] = useState(0);                  // number — выведено
const [name, setName] = useState('');                    // string

const [user, setUser] = useState<User | null>(null);     // нужно явно!
const [items, setItems] = useState<Item[]>([]);          // иначе never[]
const [state, setState] = useState<Analysis>({ status: 'idle' });
```

Правило: когда начальное значение `null` или пустой массив, вывод даёт бесполезный тип — аннотируй параметром.

**Ленивая инициализация** — когда начальное значение дорого вычислить:
```tsx
const [table, setTable] = useState(() => buildWindowTable(4096));
```
Функция вызовется один раз при монтировании. Без стрелки `buildWindowTable(4096)` выполнялся бы **на каждом рендере**, а результат отбрасывался.

# Часть 2. Проработка

## Задача. Оживляем панель

Возвращаемся к `dsp-panel` из урока 14. Делаем конфигурацию редактируемой.

```tsx
// src/App.tsx
import { useState } from 'react';
import { WINDOWS, FFT_SIZES, type FftConfig, type WindowFn, type FftSize, type Analysis } from './types';
import { ConfigView } from './ConfigView';
import { StatusLine } from './StatusLine';

export default function App() {
  const [config, setConfig] = useState<FftConfig>({
    size: 1024,
    window: 'hann',
    overlap: 0.5,
  });

  const [analysis, setAnalysis] = useState<Analysis>({ status: 'idle' });

  // производное — считаем, не храним
  const resolution = 44100 / config.size;
  const hopSize = Math.round(config.size * (1 - config.overlap));

  return (
    <main>
      <h1>DSP-панель</h1>

      <label>
        Размер FFT
        <select
          value={config.size}
          onChange={e => setConfig(c => ({
            ...c,
            size: Number(e.target.value) as FftSize,
          }))}
        >
          {FFT_SIZES.map(s => <option key={s} value={s}>{s}</option>)}
        </select>
      </label>

      <label>
        Окно
        <select
          value={config.window}
          onChange={e => setConfig(c => ({
            ...c,
            window: e.target.value as WindowFn,
          }))}
        >
          {Object.entries(WINDOWS).map(([key, info]) => (
            <option key={key} value={key}>{info.label}</option>
          ))}
        </select>
      </label>

      <label>
        Перекрытие: {Math.round(config.overlap * 100)}%
        <input
          type="range" min={0} max={0.9} step={0.05}
          value={config.overlap}
          onChange={e => setConfig(c => ({
            ...c,
            overlap: Number(e.target.value),
          }))}
        />
      </label>

      <ConfigView config={config} />
      <p>Разрешение: {resolution.toFixed(2)} Гц/бин, шаг {hopSize} отсчётов</p>
      <StatusLine analysis={analysis} />
    </main>
  );
}
```

**Что здесь стоит разобрать.**

**Функциональная форма везде.** `setConfig(c => ({ ...c, size }))`, а не `setConfig({ ...config, size })`. Второе тоже работает, но первое надёжнее: не зависит от замыкания, корректно при пакетировании нескольких обновлений подряд.

**Скобки вокруг объекта** в стрелке обязательны: `c => ({ ... })`. Без них `{` парсится как начало тела функции.

**`as FftSize` и `as WindowFn`** — вынужденные. `e.target.value` всегда `string`, DOM не знает про наши типы. Это граница с внешним миром, и приведение здесь честное — значения приходят из того же массива, которым отрисован список. Строгий вариант — валидировать:
```tsx
const parseWindow = (v: string): WindowFn =>
  v in WINDOWS ? v as WindowFn : 'hann';
```

**Производные значения считаются в теле компонента.** `resolution` и `hopSize` не в состоянии — их невозможно рассинхронизировать с `config`.

**`key` в списках** — здесь безопасно использовать сами значения, они уникальны и стабильны.

**Имитация анализа — проверка на понимание пакетирования:**
```tsx
function runAnalysis() {
  setAnalysis({ status: 'running', progress: 0 });
  const t0 = performance.now();

  let p = 0;
  const id = setInterval(() => {
    p += 0.1;
    if (p >= 1) {
      clearInterval(id);
      setAnalysis({
        status: 'done',
        bins: new Float32Array(config.size / 2),
        elapsedMs: Math.round(performance.now() - t0),
      });
    } else {
      setAnalysis({ status: 'running', progress: p });
    }
  }, 100);
}
```

Здесь спрятан stale closure: `config.size` внутри интервала — значение из того рендера, где запустили. Если пользователь поменяет размер во время «анализа», результат будет от старого конфига. Пока это даже логично, но механику отследи — в уроке 19 разберём, как с этим обращаться правильно.

**Эксперимент на реконсиляцию.** Добавь в `StatusLine` собственное состояние:
```tsx
const [expanded, setExpanded] = useState(false);
```
Раскрой его, потом смени статус анализа. Состояние сохранится — компонент в той же позиции. Теперь оберни его в `<div key={analysis.status}>` и повтори: состояние сбрасывается при каждой смене статуса. Это `key` как управление тождеством.
